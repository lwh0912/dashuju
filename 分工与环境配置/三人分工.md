# 2026 大数据挑战赛：三人分工与环境配置终稿

> 项目：青光眼眼底图像二分类。
> 执行原则：三人均参与代码开发；B 统一负责 Git 分支汇总与主分支合并；三台 GPU 并行承担不同实验。
> 本文整合分工与环境操作手册，不替代数据检查报告。赛题要求以所提供的官方截图及后续通知为准。

## 一、比赛目标与共同约定

- 输入彩色眼底图像，输出青光眼阳性概率。标签 1 为阳性，0 为阴性。
- 训练集 51,396 张，官方验证集 5,849 张，测试集 5,855 张。
- 排名首先比较 AUROC，仅当 AUROC 相同时以 AUPRC 辅助排序。召回率、精确率和混淆矩阵用于解释错误，不以 Accuracy 作为主要选择依据。
- 每天最多提交 2 次，由 A 统筹实际提交。只改变分类阈值而不改变预测概率，不会提高由这些概率计算的 AUROC/AUPRC。
- 初赛提交 `submission.csv`；复赛还需按要求提交模型。题面列出模型文件压缩前总大小 ≤500MB，单张图像端到端推理延迟 ≤100ms；从建模阶段即考虑这两个约束。
- 所有人至少独立跑通一次“读取数据→训练→验证→加载权重→测试集预测→CSV 校验”。
- 只使用赛事允许的数据与资源。外部预训练权重是否允许，需根据赛方答复确定；答复前保留不依赖外部权重的基线。

## 二、三人分工

### 2.1 总览与投入分配

| 队员 | 主责 | 必须亲自开发的代码 | 其他责任 |
| --- | --- | --- | --- |
| A：模型与训练负责人 | 基线、骨干网络、训练策略、模型融合 | 模型定义、训练入口、模型配置、融合代码 | 汇总实验结论、最终模型决策与提交 |
| B：数据策略与 Git 集成负责人 | 数据读取、增强、不平衡处理 | Dataset、增强流水线、采样器/损失策略、错误样本分析工具 | 初始化仓库、维护分支规范、统一合并到 main |
| C：验证与推理工程负责人 | 验证协议、指标、推理、性能优化 | 划分/CV、评估、推理入口、CSV 校验、性能测试工具 | 环境验收、依赖锁定、最终复现验收 |

总投入以三人各约 1/3 为起点，按实际工时和交付难度每周调整，不按代码行数或提交次数判断贡献。B 预留约 10%–15% 的个人时间做 Git 集成；C 从第一阶段就开发共享工具，并运行性能及候选方案复核实验。

### 2.2 A 的任务与验收

1. **基线开发。** 先选 ResNet18/ResNet50 或 EfficientNet-B0 中的一种，完成二分类模型、训练循环、配置读取、权重保存与恢复。外部预训练未经确认时用 `weights=None`。
2. **统一训练入口。** 调用 B 的 Dataset/采样与 C 的评估函数，不另写一套互不兼容的数据和指标逻辑。支持随机种子、数据路径、输入尺寸、batch size、学习率和实验名配置。
3. **模型实验。** 基线稳定后最多先比较 2–3 个候选骨干；先固定划分和其他条件，每轮只改一个关键因素。记录训练时间、显存、AUROC/AUPRC、输入尺寸与权重大小。
4. **融合与 TTA。** 仅对有互补验证结果的方案尝试；评估融合后总权重大小与完整推理耗时，最终以可复现收益和资源约束共同决定。
5. **最终提交。** 选定模型、配置和权重，使用 C 的推理与校验工具生成结果，保留提交记录和产物版本。

验收：有一套可复现的基线、候选模型对照表和最终方案；从 main 的固定提交能训练或加载对应权重并推理。

### 2.3 B 的任务与验收

1. **数据模块开发。** 统一 CSV 与图片路径解析，处理文件名大小写映射；返回模型需要的图像和标签，并保留原始样本标识。不同机器的绝对路径通过参数或环境变量传入。
2. **增强开发。** 先实现温和翻转、旋转和色彩扰动；裁剪要避免丢掉关键眼底区域。训练增强与验证/推理预处理分离，强度和开关写入配置。
3. **不平衡实验。** 在同一基线上逐项比较普通 BCE、类别权重、阳性过采样、Focal Loss。先单独验证再考虑组合，避免把采样与大权重同时叠加造成过度补偿。欠采样作为后续选项，先保留阴性样本信息。
4. **错误分析工具。** 导出带样本标识、真实标签、预测概率的结果，辅助查看 FN/FP 与失败类型；未经依据不修改标签或删除困难样本。
5. **Git 集成。** 建仓、维护 main、汇总 A/C 分支，核对复核意见和快速检查结果后合并。冲突涉及业务逻辑时与原作者共同解决。

验收：有可复用数据与增强模块、至少一组不平衡方法对照，以及能运行的 main。B 自己的代码由 A 或 C 复核后，再由 B 合并。

### 2.4 C 的任务与验收

1. **验证工具开发。** 固定随机种子与划分清单，提供统一评估入口、逐样本预测保存和实验汇总。若有患者/分组标识则检查分组泄漏；没有就记录限制。
2. **验证策略。** 第一阶段先用官方验证集跑通与比较基线；候选方案减少后，再按算力使用训练集固定分层划分或 3 折复核。官方验证集不参与梯度更新。不要对所有试验一开始就做完整 K 折。
3. **统一指标。** 对阳性概率计算 AUROC/AUPRC，写清 AUPRC 使用 AP 还是 PR 曲线积分；赛方公开评测代码后对齐。AUROC 不输入 0/1 预测标签。保存每折结果；有多折时同时记录折间波动与 OOF 结果。
4. **推理与提交工具。** 实现权重加载、固定预处理、批量推理与 CSV 输出；编写提交校验器，检查 5,855 个测试标识恰好各出现一次，列名、数值范围及标签合法。
5. **工程优化实验。** 比较 AMP、DataLoader、batch size 与数据加载开销；输出可复用代码和至少一组有对照的结果。显存不足先减 batch size，使用梯度累积时记录有效 batch size。
6. **性能与复现。** 开发单图端到端计时、权重总大小检查和环境自检；记录设备、预热、CUDA 同步、batch=1、计时边界与多次测量结果。训练卡更快不代表在赛方 T4 上满足 100ms。

验收：评估、推理、校验与 benchmark 都有可运行脚本；有工程优化对照结果；能从干净代码与固定依赖复现最终预测。合并操作交给 B，C 提供可自动运行的检查工具。

## 三、代码边界与协作方式

### 3.1 仓库结构

以下文件是团队要开发的交付项，不代表本文已经附带了训练项目代码。

```text
code/
├── configs/                  # 实验配置，随所属模块修改
├── src/
│   ├── data/                 # B：数据读取、增强、采样
│   ├── losses/               # B：不平衡损失
│   ├── models/               # A：骨干与分类头
│   ├── train.py              # A：训练入口
│   ├── evaluate.py           # C：统一评估
│   ├── infer.py              # C：统一推理
│   └── ensemble.py           # A：融合
├── tools/
│   ├── make_splits.py        # C，B 提供数据/分组信息
│   ├── validate_submission.py# C
│   ├── benchmark.py          # C
│   └── analyze_errors.py     # B
├── splits/                   # 固定划分清单；限制仓库访问
├── docs/                     # 接口、实验结论、运行说明
├── requirements-extra.lock.txt # C 锁定并由 B 合并的额外依赖
└── README.md                 # C 维护运行方法，B 检查集成一致性
```

统一接口：图像为 RGB Tensor；二分类模型输出与损失函数匹配的 logits；评估和推理统一转换为标签 1 的概率。使用 `BCEWithLogitsLoss` 时，训练损失前不重复 sigmoid。标准化、缩放和裁剪规则随配置与权重一起保存。训练与最终推理的预处理必须对齐。

### 3.2 Git 规则

- main 保存当前可运行版本，由 B 执行汇总合并。三人都在自己的功能分支开发，不直接向远程 main 推送开发中的改动。
- A/C 的改动由 B 组织复核；模型或数据逻辑请对应负责人参与。B 的改动由 A/C 至少一人复核。
- 合并前至少检查：能导入、配置能加载、少量样本前向/评估或相关脚本能运行。由提交者先自测，C 提供共享检查脚本，B 最终确认。
- 不向 Git 提交数据集、权重、完整日志、缓存、凭据和预测大文件；训练产物单独备份。
- 每次实验登记：负责人、Git commit、配置、数据版本、划分、种子、GPU、指标、耗时、权重路径。三台机器启动前先认领实验，避免重复计算。
- 每天用 10–15 分钟同步已完成结果、阻塞和下一组实验。B 集中处理合并，不要求每次小改动立即打断当前任务。

### 3.3 三台 GPU 的使用

| 阶段 | A 的机器 | B 的机器 | C 的机器 |
| --- | --- | --- | --- |
| 基线期 | 跑主基线 | 检验数据模块与增强，跑小规模对照 | 检验评估/推理，跑性能基准 |
| 改进期 | 候选模型/训练设置 | 相同基线上的采样/损失/增强实验 | 工程优化、候选方案复核 |
| 冲刺期 | 候选模型或一个折 | 另一候选/折 | 其余折及最终验收 |

按实际显存调整 batch size；显卡型号不必相同。做算法对比时记录有效 batch size、输入尺寸和训练预算；跨卡训练速度不能直接作为算法优劣证据。

## 四、环境路线与命令行说明

### 4.1 采用哪条路线

本手册以 Windows 10/11 + NVIDIA 显卡为主要操作场景：**Windows 驱动 → WSL2 Ubuntu → Docker Desktop 的 WSL2 后端 → 比赛容器**。Windows 版本还需满足 Docker Desktop 当前支持要求。已有可用的原生 Linux GPU Docker 环境可跳到 5.4；原生 Linux 需要单独配置 NVIDIA Container Toolkit，见 5.10。

“显卡能用”还需确认型号。本手册的 CUDA 操作适用于受相应驱动和 PyTorch 构建支持的 NVIDIA GPU；如果有人使用 AMD/Intel GPU，由 C 单独安排兼容环境或共享 NVIDIA 计算资源，不能套用 `--gpus all` 就认为 CUDA 可用。

| 执行位置 | 怎么打开 | 本文用途 |
| --- | --- | --- |
| 管理员 PowerShell | 开始菜单搜索 PowerShell，右键“以管理员身份运行” | 安装/更新 WSL |
| 普通 PowerShell | 开始菜单或 Windows Terminal 的 PowerShell 标签 | 查显卡、进入 Ubuntu |
| Ubuntu 终端（WSL） | 开始菜单打开 Ubuntu，或 PowerShell 执行 `wsl -d Ubuntu-24.04` | Docker 命令、Git、文件管理 |
| 容器内 Bash | Ubuntu 终端执行下文 `docker exec` | Python 自检、训练、推理、依赖安装 |

本文 `bash` 代码块均明确标注位置。带 `\` 换行的 Linux 命令应在 Ubuntu/Bash 中执行，不直接粘贴到 PowerShell 或 CMD。代码块内不包含需要手动输入的 `$` 提示符。

### 4.2 推荐环境与个人机器的区别

| 项目 | 题面列出的目标环境 | 个人开发说明 |
| --- | --- | --- |
| GPU | NVIDIA T4 16GB ×1 | 可用其他兼容 NVIDIA GPU；记录型号与显存 |
| CPU / 内存 / 磁盘 | 8 核 / 32GB / ≥100GB SSD | 留出镜像、数据、缓存和多份权重空间 |
| 驱动 | ≥570.117，配套 CUDA 12.8 | Windows 安装适配本机显卡的 NVIDIA 驱动，并实际验证容器 |
| 容器 CUDA / cuDNN | CUDA 12.8 / cuDNN 9 | 优先使用官方推荐镜像 |
| Python | 3.12 | 在容器内核对 |
| PyTorch / torchvision | 2.10.0 / 0.25.0 | 在容器内核对，版本可能含 `+cu128` 后缀 |

`nvidia-smi` 顶部的 CUDA Version 是驱动可支持的 CUDA 版本上限，不等同于容器内 PyTorch 使用的 CUDA 版本。容器内看 `torch.version.cuda`。普通 PyTorch 使用不要求再在 Windows/WSL 安装一套 CUDA Toolkit；WSL 内不要安装 Linux NVIDIA 显示驱动覆盖 Windows 映射的驱动。
